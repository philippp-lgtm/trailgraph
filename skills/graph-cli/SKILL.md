# graph CLI

`graph` reads and writes knowledge graphs. Every graph has an ontology that
fixes its types, fields, relations and lifecycles; every write is validated
against it and audited. The CLI is on `PATH`.

## Ground rules

- Pass `--json` to every command and read the envelope (below), not the text;
  only the module views of step 2 read better as text.
- The live CLI wins. If this skill and `graph describe commands --json` or
  `--help` disagree, trust the CLI.
- If a skill for the selected graph exists, read it first: it names the
  graph's types, fields and relations. This skill never does.
- Never guess a type, field, relation or state name. Ask `graph describe`.
- Run each call as a plain command that starts with `graph`: no `cd`,
  variables, loops, pipes or heredocs, which a restricted harness refuses.
  If a call is refused, run it again in that form before you give up.
- Reads never change anything. `graph skills`, `self update` and `connect`
  install agent skills such as this one, and the program: run them only
  when the user asks. `graph skills check` and `--check` only read.

## Workflow

1. Pick a graph: `graph graphs --json` lists the graphs you may use. Select
   one with `--graph <graph>` on every command. A project may preset a
   default; use it unless the user names another graph.
2. Learn the model: `graph describe types --json`, then
   `graph describe type <type> --json`: fields with datatype, enum `values`,
   `limits` and `role`; relations with their `qualifiers` (values on the edge);
   lifecycles with states, transitions and the `guards` a dry run checks.
   On a graph with several modules (subject areas) start with
   `graph describe modules`, then `graph describe module <module>` (their text
   is made for reading and less than half the size of `--json`) or, for a
   term you can only name, `graph describe search <value> --json`
   (types, relations, fields, values; not data); never dump the whole schema.
3. Read: `graph find --type <type> --where <attr>=<value> --json`,
   `graph get <id> --json`, `graph neighbors <id> --json`. Lists are
   paged: follow `page.next_offset` or the hint until `page.truncated` is
   false. To find something by name, `graph lookup <value> --json` lists
   the candidates named exactly so (`--match prefix` adds names that
   start with it), since names are not unique; give several names as
   separate arguments, quoted if they hold spaces. Use a returned id only
   when its name has exactly one exact match (`data.texts[].exact` is 1);
   otherwise list the candidates and ask which one is meant, then answer.
4. `graph search <value> --json` searches names and every text field,
   forgiving case, accents, typos and parts of words. Its results are
   suggestions: read one with `graph get` before you use it.
5. Before a create, search for the name and its short forms; if the same
   thing exists, add the new name to it with `graph update --add` instead. Put
   abbreviations and synonyms into `alt_label` fields, misspellings into
   `hidden_label` fields.
6. Preview a write that adds entities or is hard to take back (`create`,
   `apply`, `supersede`, `retract`, `transition`) with `--dry-run --json`;
   one `update`, `link` or `unlink` may run directly (undo: `update`, `unlink`).
7. Read `data.findings` of every write: on `data.semantic.possible_duplicate`
   reuse a candidate from `actual` or tell the names apart, on
   `data.structural.deprecated_term` use the replacement its message names.

## Questions across relations

`graph query` answers a read-only Cypher query in one call. Use it when a
question needs several hops, OR or NOT across relations, or counts; `find`,
`neighbors` and `lookup` stay the simple path for one type, one hop or a
name. `graph describe schema --json` lists the patterns a query can use.
Read [references/query.md](references/query.md) before the first query.

## History and what goes into a graph

A graph holds its subject (its skill names what counts), each fact in its
field or relation, never repeated in a text. How you worked (what you read
and how, what you checked, a doubt) goes to the user and into `--reason`,
which each revision keeps; it is required for `supersede`, `retract` and
when `graph whoami` lists `require_reason`. Details: [references/history.md](references/history.md).

## Writing safely

- Pass `--idempotency-key` with a key of your choice. A dry run does not
  use it up. Repeating the same command with the same key never writes
  twice: it returns the first result (`idempotent_replay` is true).
  Without a key, check `graph history <id> --json` before a retry.
- `graph update --add <attr>=<value>` (or `--remove`) adds one list value
  without a read; `--set-json` replaces the list. No change: `entity.unchanged`.
- When a write depends on what you read, pass `--expect` with that `rev`
  so that a concurrent change is a conflict, not a lost update (`graph
  get`: `data.entity.rev`; a write: the new one in `data.entities[].rev`).
- Fix a wrong value with `graph update`; the history keeps the old one.
  Nothing is deleted: `graph supersede <id> <id>` when a newer entity (the
  first id) replaces older ones, `graph retract` when one is withdrawn,
  `graph unlink` for a wrong edge. States change with `graph transition`.
  On `data.referential.target_referenced` read [references/errors.md](references/errors.md).
- Prefer the single-operation commands. `graph apply` takes change set
  documents for batches: write the document to a file in the working
  directory, dry-run it with `graph apply <file> --dry-run --json`, then
  apply it; `--summary` leaves out the list of entities. Read
  [references/changesets.md](references/changesets.md) before the first.

## Access

- `graph whoami --json` shows who you act as and, per graph in
  `data.permissions.graphs`, your `level` (`read` or `write`), the actions
  withheld anyway (`withheld`), the types you may only read and the
  obligations (`require_reason`, `max_batch`). Check it before you write.
- A graph you may not use does not exist for you: `graph graphs` does not
  list it, and selecting it gives `graph.not_found`.
- On `access.denied`, stop and tell the user what was refused
  (`error.details`). Access is set by the maintainer of the installation.
  Never edit the project's pointer file, a policy or the data directory to
  get around it, and never retry under another identity.
- The warning `access.project_unknown` means the project has no access of
  its own yet and gets the access for no project. Go on within what
  `graph whoami` shows, and tell the user once that the maintainer can give
  the project its own access. Never change the project name to get more.

## Files

Graphs whose ontology imports the `files` module store files: scans,
documents, saved web pages. When facts come from a file, read
[references/files.md](references/files.md) first: store the file, link what
you take from it, never edit a stored file.

## Output envelope

Every `--json` call prints one JSON object on stdout.

- Keys, always present: `schema`, `ok`, `command`, `graph`, `data`, `page`, `hints`, `warnings`, `error`.
- `ok` tells success; `data` holds the result, `page` the paging of lists.
- Never cut an answer with `head`, a pipe or another program: ask for less.
  `--fields <attr>,<attr>` on `get`, `find` and `neighbors` keeps those
  fields and `rev`; `RETURN` in `graph query`; `describe schema --compact`.
- A large answer goes to a file (`output.spilled`, `details.path`; `data`
  null): ask for less, or read parts with your file tools, never `jq`.
- On failure `error` holds `code`, `category`, `retryable`, `message`, `hint`, `details`. `hint` is the command to run next, or null.
